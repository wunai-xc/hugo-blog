## 一、Frontmatter（文件头元信息）

每篇文章**必须**以 frontmatter 开头，两种格式都可：

### TOML 格式（推荐，用 `+++` 包裹）

```
toml
+++
title = '文章标题'
date = 2026-08-03
draft = false
tags = ["标签1", "标签2"]
categories = ["分类"]
summary = '一句话摘要，显示在文章列表'
+++
```

### YAML 格式（用 `---` 包裹）

```
yaml
---
title: "文章标题"
date: 2026-08-03
draft: false
tags: ["标签1", "标签2"]
categories: ["分类"]
summary: "一句话摘要"
---
```

**字段说明**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `title` | 是 | 文章标题 |
| `date` | 是 | 发布日期（影响排序） |
| `draft` | 否 | `true` 时不发布，默认 `false` |
| `author` | 否 | **作者信息**。填 `"AI"`（不区分大小写）→ 首页卡片文字整体变蓝 + 详情页顶部红色警示徽章；填其他字符串（如 `"wunai"`）→ 灰色普通徽章。留空则继承站点默认（`hugo.toml` 中 `author` 字段）。详见下文「十五、作者信息与 AI 标记」。 |
| `tags` | 否 | 标签列表 |
| `categories` | 否 | 分类列表 |
| `summary` | 否 | 列表页摘要 |

> **注意**：`draft = true` 的文章本地 `hugo server -D` 能看到，但上线时不部署。要发布记得改成 `false` 或删除该行。

## 七、图片与链接

### 本地图片（推荐）

把图片放在 `static/images/你的目录/` 下，文章里用 `/images/你的目录/文件名` 引用：

```
markdown
![替代文字](/images/cell/animal-cell.svg)
*图片说明（斜体）*
```

**目录结构示例**：

```
static/
└── images/
    └── cell/
        ├── animal-cell.svg
        └── plant-cell.png
```

### 外链图片（不推荐，可能加载慢）

```
markdown
![替代文字](https://example.com/image.png)
```

### 带说明的图片

```
markdown
![细胞结构](/images/cell/animal-cell.svg)
*图 1：典型动物细胞结构。图源：LadyofHats, CC0*
```

> **小提示**：用 `<small>` 标签可以让图源说明更小：

```
markdown
<small>图源：Wikimedia Commons, CC0</small>
```

### 文件夹收纳（Leaf Bundle，长文推荐）

当一篇文章配图很多、或者要附带 PDF/附件时，推荐把文章组织成**文件夹**而不是单个 `.md`：

```
content/zh/posts/我的文章/
├── index.md          ← 这篇文章的正文（frontmatter 写在这里）
├── cover.png         ← 封面图（frontmatter 里 cover.image = "cover.png"）
├── 1-封面.jpg        ← 任意随文图片
├── diagram.svg       ← SVG 图
├── 附件.pdf          ← 同目录可以放任意资源
└── ...
```

正文里用 `./` 相对路径引用同目录资源即可：

```
markdown
![封面](./cover.png)
![第一章插图](./1-封面.jpg)
[下载附件](./附件.pdf)
```

**两种写法对比**：

| 写法 | 单文件 `.md` | 文件夹 `index.md`（Leaf Bundle） |
|------|-------------|--------------------------------|
| 文章位置 | `content/zh/posts/我的文章.md` | `content/zh/posts/我的文章/index.md` |
| 配图位置 | `static/images/我的文章/pic.png` | 同文件夹，如 `我的文章/pic.png` |
| 引用写法 | `![](/images/我的文章/pic.png)` | `![](./pic.png)` |
| 最终 URL | `/zh/posts/我的文章/` | `/zh/posts/我的文章/`（完全相同） |
| 列表 / 左栏 / 面包屑 / TOC | ✅ 一致 | ✅ 一致 |

**封面图写法差异**：

```toml
# 文件夹（Leaf Bundle）— 不加 /，走同目录资源
[cover]
image = "cover.png"

# 单文件 — 加 / 前缀，走站点 static
[cover]
image = "/images/我的文章/cover.png"
```

> **已有单文件升级为文件夹**：新建同名文件夹 → 把原 `.md` 改名为 `index.md` → 把配图搬进来 → 正文里的图片路径改成 `./xxx`。**URL 完全不变**，不影响 RSS / 搜索 / 已有外链。

### 多文章收纳（合集，自动检测）

上面讲的是「一篇文章 + 配图」用一个文件夹（`index.md`）。如果**同一主题有多篇文章**，把它们扔进一个文件夹，再加一个**空的 `_index.md`**（Hugo 生成列表页的必需标记，里面什么都不用写）：

```
content/zh/posts/Claude/
├── _index.md          ← 空文件！只需存在，内容留空（+++ +++）
├── 01-上下文窗口.md
├── 02-付费计划账单.md
└── ...
```

> 为什么需要空 `_index.md`？Hugo 只有看到 `_index.md`（带下划线的分支标记）才会把文件夹识别成「可点击的列表页」。没有它，文件夹只是普通子目录，点进去会 404。但这个文件**完全不用写内容**——标题、日期、篇数都自动派生。

网站会**自动检测**：文件夹里有 2 篇及以上文章时，首页和列表页把它显示为一张**堆叠卡片**（占用一个格子，右上角标篇数），点进去是该文件夹的文章列表，再选要读哪一篇。

| 情况 | 文件夹内容 | 首页展示 |
|------|-----------|---------|
| 单篇文章 | `我的文章/index.md` + 配图 | 普通文章卡片（Leaf Bundle） |
| 多篇合集 | `Claude/_index.md`（空）+ `01.md`、`02.md` … | 堆叠卡片，标题=文件夹名，徽章=篇数 |
| 只有 1 篇 | `Claude/_index.md`（空）+ `01.md` | 按普通文章显示，不视为合集 |

**要点**：

- `_index.md` 是**空文件**，不用写任何 front matter
- 卡片标题自动取**文件夹名**（如 `Claude`），徽章显示「N 篇」
- 卡片日期自动取文件夹内**最新一篇文章**的日期
- 想自定义标题/描述？在 `_index.md` 写 `title = "..."` 即可覆盖，不写就用文件夹名

## 九、化学符号（mhchem）

### 化学式

```
markdown
水是 $\ce{H2O}$，食盐是 $\ce{NaCl}$。
```

效果：水是 $\ce{H2O}$，食盐是 $\ce{NaCl}$。

### 化学方程式

```
markdown
$$
\ce{2H2 + O2 -> 2H2O}
$$
```

效果：

$$
\ce{2H2 + O2 -> 2H2O}
$$

### 可逆反应与条件

```
markdown
$$
\ce{N2(g) + 3H2(g) <=>[高温、高压][催化剂] 2NH3(g)}
$$
```

效果：

$$
\ce{N2(g) + 3H2(g) <=>[高温、高压][催化剂] 2NH3(g)}
$$

### 同位素（注意转义下划线）

> **重要**：化学公式里的下标 `_` 必须写成 `\_{}`，否则会被 Markdown 误解析为斜体。

```
markdown
碳-14 写作 $\ce{^{14}\_{6}C}$，铀-235 写作 $\ce{^{235}\_{92}U}$。
```

效果：碳-14 写作 $\ce{^{14}\_{6}C}$，铀-235 写作 $\ce{^{235}\_{92}U}$。

### 沉淀与气体符号

```
markdown
$$
\ce{Ag+ + Cl- -> AgCl v}
$$
$$
\ce{Zn + 2H+ -> Zn^{2+} + H2 ^}
$$
```

效果：

$$
\ce{Ag+ + Cl- -> AgCl v}
$$
$$
\ce{Zn + 2H+ -> Zn^{2+} + H2 ^}
$$

### 氧化还原反应

```
markdown
$$
\ce{2KMnO4 + 16HCl -> 2KCl + 2MnCl2 + 5Cl2 ^ + 8H2O}

```

效果：

$$

## 十一、文本标记增强

### 11.1 引用标记 `[reference:N]`（自动转换）

从 NotebookLM 等 AI 工具复制内容时常带的引用标记，**会被自动渲染成上标编号**：

```
markdown
图灵机由图灵于 1936 年提出[reference:1]，是计算理论的基石[reference:2][reference:3]。
```

效果：图灵机由图灵于 1936 年提出[reference:1]，是计算理论的基石[reference:2][reference:3]。

> 鼠标悬停在编号上会显示「引用 N」提示，无需手动处理这些标记。

### 11.2 高亮文本 `==文字==`（GitHub 扩展语法）

用两个等号包裹文字，**自动渲染成黄色荧光笔高亮**：

```
markdown
这是==重点内容==，注意 ==这里== 也很关键。
```

效果：这是==重点内容==，注意 ==这里== 也很关键。

> 暗色主题下高亮会自动变得柔和。

### 11.3 行内彩色文字 `{{</* color */>}}`

用 shortcode 给文字上色，支持 9 种预设颜色名或任意 hex 色值：

````
markdown
{{</* color red */>}}红色警告{{</* /color */>}}
{{</* color green */>}}绿色成功{{</* /color */>}}
{{</* color blue */>}}蓝色信息{{</* /color */>}}
{{</* color "#7048e8" */>}}自定义紫色{{</* /color */>}}
````

效果：

- {{< color red >}}红色警告{{< /color >}}
- {{< color green >}}绿色成功{{< /color >}}
- {{< color blue >}}蓝色信息{{< /color >}}
- {{< color "#7048e8" >}}自定义紫色{{< /color >}}

**支持的预设颜色名**：`red` `orange` `yellow` `green` `cyan` `blue` `purple` `pink` `gray`/`grey`

### 11.4 行内带色标记块 `{{</* mark */>}}`

类似荧光笔，但带背景色和边框，更显眼。支持 9 种预设颜色：

````
markdown
{{</* mark yellow */>}}默认黄色{{</* /mark */>}}
{{</* mark red */>}}红色标记{{</* /mark */>}}
{{</* mark green */>}}绿色标记{{</* /mark */>}}
{{</* mark blue */>}}蓝色标记{{</* /mark */>}}
````

效果：

{{< mark yellow >}}默认黄色{{< /mark >}} {{< mark red >}}红色标记{{< /mark >}} {{< mark green >}}绿色标记{{< /mark >}} {{< mark blue >}}蓝色标记{{< /mark >}}

**完整颜色列表**：`red` `orange` `yellow` `green` `cyan` `blue` `purple` `pink` `gray`/`grey`

### 11.5 四种标记方式的选择

| 方式 | 语法 | 适用场景 |
|------|------|---------|
| `[reference:N]` | AI 工具自动带 | 从 NotebookLM 等 AI 复制内容时无需处理 |
| `==高亮==` | 双等号 | 简单强调，无需 shortcode |
| `{{</* color 红 */>}}` | shortcode | 需要精确控制文字颜色 |
| `{{</* mark 红 */>}}` | shortcode | 需要带背景色的醒目标记 |

## 十五、作者信息与 AI 标记

本站的 `author` frontmatter 字段不仅是简单的文字署名，还会触发**首页卡片变色**和**详情页徽章**两个视觉提示，帮读者一眼区分「人类原创」和「AI 生成/整理」的内容。

### 15.1 支持的取值与效果对照

| 写法 | 首页卡片效果 | 详情页顶部徽章 | 适用场景 |
|------|-------------|---------------|---------|
| `author = "AI"` | 标题/摘要/元信息**整体变蓝**（浅色模式 `#3b82f6`，深色模式 `#3a6fff`） | 🔴 **红色胶囊徽章**：「注意⚠️ 本文由 AI 生成，可能存在误区，斟酌阅读！！」 | AI 生成、AI 整理润色、AI 扩写的文章（即使有人工校对也建议标 AI） |
| `author = "wunai"` | 无变色（默认黑白灰） | ⚪ **灰色胶囊徽章**：「作者：wunai」 | 人类作者原创的文章 |
| `author = "任意字符串"` | 无变色 | ⚪ **灰色胶囊徽章**：「作者：任意字符串」 | 多作者、转载标注、笔名等 |
| 不写 `author` 字段 | 无变色 | 无徽章 | 继承站点默认（当前全局默认 author 为 `"wunai"`，但 `hideAuthor=true` 时默认隐藏徽章） |

> **大小写不敏感**：`author = "ai"`、`"Ai"`、`"aI"` 都会触发 AI 标记。

#### AI 生成的文章

````

#### 人类原创的文章

````

tags = ["公告", "博客搭建"]
categories = ["笔记"]
summary = '第一次来到本站？从这里开始——介绍博客定位、搭建过程与近期新增的内容、功能。'

+++
````

### 15.3 效果预览

#### 首页卡片对比

- **AI 文章**：卡片内标题、摘要、日期、阅读时长、字数**全部呈蓝色**，和普通文章视觉区分明显
- **置顶文章（AI）**：同样会应用蓝色文字效果，不影响 pinned-badge 置顶角标

#### 文章详情页徽章

标题 + 元信息（日期/阅读时长/标签）正下方会显示一颗圆角胶囊徽章：

- 🔴 AI：`注意⚠️ 本文由 AI 生成，可能存在误区，斟酌阅读！！`（纯红底白字，不跟随主题色）
- ⚪ 其他作者：`作者：XXX`（浅灰背景 + 次级文字色，跟随主题自动适配暗色）

### 15.4 作者字段的深层作用

除了可见的UI，`author` 还会在以下位置生效：

1. **HTML `<meta name="author">`**：搜索引擎和浏览器读取的页面作者元信息
2. **JSON-LD 结构化数据**（`<script type="application/ld+json">`）：Google 等搜索引擎抓取的 schema.org 作者信息，影响知识图谱展示
3. **Service Worker 缓存逻辑**：与 AI 标识相关的样式不单独缓存（作为 CSS 内联的一部分整体缓存）

### 15.5 选择建议：什么时候标 AI？

一个实用的判断标准——**读者如果看到文章不是 AI 生成的会惊讶，就应该标 AI**。具体包括：

| 情况 | 是否标 AI |
|------|----------|
| 全文由 ChatGPT / Claude / NotebookLM / TRAE 等生成，仅人工做过错别字/格式修正 | ✅ 标 AI |
| 人类给出详细大纲 + 素材，AI 完成具体行文 | ✅ 标 AI |
| NotebookLM 生成的「AI 概览」或 Source 整理 | ✅ 标 AI |
| AI 初稿 + 人类大幅修改（修改率 >50%，加入了大量个人经验和原创内容） | ✅ 仍建议标 AI（可在文末注明「本文由 AI 初稿 + 人工深度改写」） |
| 完全由人自己一个字一个字敲出来的 | ❌ 不标（或填 `author = "wunai"`） |
| 翻译外文 + AI 辅助翻译 | ✅ 标 AI（若纯人工翻译则不标） |

> **核心原则**：宁滥勿缺。错标 AI 只是稍微降低一点「作者权威感」；但把 AI 文章冒充人写，一旦被发现会严重损害信任。AI 能力完全可以堂堂正正展示，警示徽章的存在反而让读者在关键时刻（比如医学、法律、金融类文章）多一分斟酌——这是对读者负责。

## 附录：shortcode 转义写法

在文章里**展示** shortcode 代码（而非执行），用 `{{</* ... */>}}` 包裹：

````
markdown
显示原始代码：{{</* chem smiles="CCO" */>}}

会被执行：{{< chem smiles="CCO" >}}
````

> **关键提示**：
> - shortcode 内部用 `{{</* ... */>}}` 写法可在文档中显示原始代码而不被执行
> - 文章正文里用 `{{</* ... */>}}` 去掉星号写法会被执行
> - 标题、表格里的 shortcode 必须**转义**，否则 Hugo 解析失败导致构建报错

## 附录二：AI 辅助写作的避坑提示

用 AI（ChatGPT / Claude / TRAE 等）生成 Markdown 文章时，经常遇到一个隐蔽问题：**代码块语法高亮丢失**。原因和应对方法记录如下。

### 问题成因

为了让用户方便复制，AI 常把整篇 md 内容包在**一个外层代码块**里输出。但 md 文件内部本身就有 ` ``` ` 围栏，外层和内层围栏会冲突，导致外层代码块提前闭合。

AI 的"取巧"做法是把内部的语言标识符单独换行：

````markdown
原（正确）：            ```python
AI 错误输出：           ```
                       python
````

这样内部围栏看起来不像真正的闭合符，外层代码块不会提前结束，复制功能保住了——但副作用是**复制出来的 md 里所有代码块都丢了语法高亮**，因为 ` ``` ` 后面换行的 `python` 会被渲染器当成普通文本。

### 正确做法

**方案 1（推荐）：让 AI 直接写文件，而非贴代码块输出**

在 TRAE 这类有文件写入能力的环境里，直接让 AI 用 `Edit` / `Write` 工具改 md 文件，根本不存在围栏冲突问题，格式也能保持完全正确。

**方案 2：用 4 反引号作为外层围栏**

CommonMark 规范支持用 4 个（或更多）反引号作为代码围栏，内层 3 反引号就不会冲突：

````markdown
````
# 这里是整篇 md 内容

```python
def foo():
    pass
```
````
````

复制时连外层 4 反引号一起去掉即可。

**方案 3：给 AI 明确约束**

在 prompt 里加一句约束，能避免大部分这类问题：

> 严格保持 ` ``` ` 代码围栏与语言标识符在同一行（如 ` ```python `），不要拆分、换行或转义。若需在对话中展示整篇 md，外层用 4 反引号 ` ```` ` 包裹。

### 排查方法

如果某篇文章上线后代码块全都没有颜色、变成纯文本，优先检查：

1. 源文件里 ` ``` ` 后面是否紧跟语言名（同一行，无换行）
2. 是否有多余的空行打断围栏配对
3. shortcode `{{</* */>}}` 转义是否破坏了围栏结构

> **一句话总结**：能直接写文件就别让 AI 贴代码块；非要贴，就用 4 反引号外层围栏。

| 语法类别 | 示例写法 | 渲染效果 |

## 附录四：图表与乐谱代码块语法详解

所有图表库都在用户**浏览器端渲染**（不依赖 Node/Python/Graphviz 本地二进制），Hugo 只做"把代码原文包在 `<pre class="language-xxx"><code>` 里"这件事。部署和构建不受影响。

### A4.1 Mermaid：流程图 / 时序图 / 甘特图 / 类图 / 状态图 / 饼图 / GitGraph

````markdown
```mermaid
flowchart LR
    A[开始] --> B{判断}
    B -->|是| C[成功分支]
    B -->|否| D[失败分支]
    C --> E((结束))

```
````

**更多 Mermaid 类型直接用关键字换即可**：`flowchart TD` / `sequenceDiagram` / `gantt` / `pie showData` / `classDiagram` / `stateDiagram-v2` / `gitGraph`。本站自动读取当前 PaperMod 主题（dark/light）给 Mermaid 传对应主题。渲染失败会在原位显示「Mermaid 语法错误 + 原文」红框提示，不影响文章其他部分。

### A4.3 ECharts：折线图 / 饼图 / 柱状图 / 雷达 / 词云 / 脑图 / 散点 等所有 ECharts 5 内置图

写法一：**直接写 option JSON**（最常用，推荐）

````markdown
```echarts pie
{
  "title": { "text": "全站访问来源", "left": "center" },
  "tooltip": { "trigger": "item" },
  "series": [{
    "type": "pie",
    "radius": ["40%", "70%"],
    "data": [
      { "value": 1048, "name": "搜索引擎" },
      { "value": 735,  "name": "直接访问" },
      { "value": 580,  "name": "外链引流" },
      { "value": 484,  "name": "社交分享" }
    ]
  }]
}
```
````

- info string 第一个 token 是图表类型说明（`pie` / `line` / `bar` / `radar` / `scatter` / `mindmap` / `heatmap` 等任意字符串，仅用于失败日志定位，不决定渲染行为——真正决定图的是 JSON 里的 `series[].type`）
- **data-height="500px" data-width="100%"**：可通过 `{ height="500px" }` 属性写法自定义尺寸（Hugo 代码块属性语法）

写法二：**写完整 JS，把最终 option 赋给变量 `__opt`**（适合需要用变量/循环拼装复杂数据）

````markdown
```echarts line
// 先做一些计算
var months = ['1月','2月','3月','4月','5月','6月'];
var uv = [820, 932, 901, 934, 1290, 1330];
var pv = uv.map(function(v){ return Math.round(v * 3.2); });
// 把最终 option 赋给全局变量 __opt（注意是两个下划线）
__opt = {
  title: { text: 'UV / PV 近半年趋势' },
  tooltip: { trigger: 'axis' },
  legend: { data: ['UV', 'PV'] },
  xAxis: { type: 'category', data: months },
  yAxis: { type: 'value' },
  series: [
    { name: 'UV', type: 'line', smooth: true, data: uv },
    { name: 'PV', type: 'line', smooth: true, data: pv }
  ]
};
```
````

额外扩展：已自动加载 **echarts-wordcloud**（词云）；需要 liquidfill、map、g2 等可在文章正文中用 `<script src="...">` 再手动挂一个 ECharts。

### A4.4 abc.js 五线谱（abc 记谱法）

````markdown
```abc
T: 小星星 Twinkle Twinkle
C: 莫扎特 Mozart
M: 4/4
L: 1/4
Q: 1/4=120
K: C
|: C C G G | A A G- |  F F E E | D D C4 :|
|: G G F F | E E D4 |  G G F F | E E D4 |
  C C G G | A A G- |  F F E E | D D C4 |]
```
````

abc.js 参数（可选代码块属性）：
- `staffwidth="740"`：每行谱表宽度（px），默认响应式 `resize`
- `transpose="2"`：整体移调（+2 升两个半音）

渲染失败会原位打印红色错误提示 + 原始 abc 记谱文本，便于对照修改。
